## Scope + Constraints
- Scope: all modules under `src/drunk_ai_proxy/drunk_ai_proxy` with phased, low-risk delivery.
- Priority order (mandatory):
  1. OOP class-per-module remediation
  2. Method-level SRP remediation
  3. DRY/reuse consolidation

  5. SOLID dependency/interface cleanup
- Constraints:
  - Preserve public behavior and route surface unless explicitly noted.
  - Use incremental compatibility shims for one release cycle where needed.
  - Avoid broad rewrites; use vertical slices and targeted tests per phase.

## Current-State Summary
- Strong base: provider-driven architecture, explicit FastMCP auth wiring, existing protocol interfaces, and broad tests.
- Main structural debt: duplicated construction paths, layering leak (`proxies -> app` cache imports), mixed-concern orchestration methods, and partially procedural utility modules.
- Highest-risk hotspots:
  - `app/middleware_provider.py`
  - `utils/security.py`
  - `app/server.py`
  - `proxies/mcp/base_provider.py`
  - `proxies/llm/proxies_provider.py`

## Phased Plan

### Phase 1 — OOP + SRP Remediation (Mandatory First)
**Goal:** enforce class-first module structure and one-concern public methods without changing observable behavior.

Tasks:
1. Refactor `app/middleware_provider.py` to one canonical `MiddlewareProvider.build()` path.
2. Refactor `utils/security.py` to a single primary class API and remove alias rebinding duplication.
3. Introduce class-first wrappers in `utils/env_resolver.py`, `utils/config_yaml_uri.py`, and `proxies/mcp/resource_path_utils.py`.
4. Introduce `EnvConfig` snapshot object in `utils/env.py` and migrate consumers incrementally.
5. Split mixed-concern methods from SRP inventory (SRP-01..SRP-04) into focused helpers.

Dependencies: none (first gate).

Acceptance Criteria:
- No module-level business orchestration remains in scoped P0 modules.
- All four SRP targets have helper extraction and reduced method responsibility.
- Existing API behavior remains unchanged.

### Phase 2 — DRY Cleanup + Reusable Abstractions
**Goal:** remove repeated logic and establish reusable internal abstractions.

Tasks:
1. Build `RemoteProviderBootstrapContext` and generic `_attach_remote_entries` in `McpBaseProvider`.
2. Unify overlap warning logic and runtime client/cache construction in one reusable path.
3. Remove duplicated middleware/security construction code paths.
4. Consolidate shared validation/conversion helpers in LLM endpoint flow where repeated.

Dependencies: Phase 1 complete.

Acceptance Criteria:
- Remote resource attachment path uses one reusable abstraction for skill/agent/prompt.
- Middleware and security assembly each have one canonical construction path.
- Duplicate code blocks are removed with no regression in tests.

### Phase 3 — Library-Native FastMCP/FastAPI Adoption
**Goal:** replace hand-rolled implementations with framework-native capabilities where functionally equivalent.

Tasks:
1. Use FastAPI-native router/docs mechanisms for LLM sub-app endpoints; reduce custom OpenAPI assembly in `swagger_provider` when possible.
2. Revisit provider contracts so only mountable providers implement mount behavior.
3. Keep explicit FastMCP auth provider construction and route-level dependency patterns already aligned with current docs.

Dependencies: Phase 1 complete; Phase 2 preferred.

Acceptance Criteria:
- No no-op contract methods remain for mount behavior.
- OpenAPI generation code is reduced and delegated to native framework docs for covered routes.
- Endpoint behavior and schemas remain compatible.

### Phase 4 — SOLID Remediation and Layering Hardening
**Goal:** enforce DIP/OCP/ISP boundaries and stabilize extension points.

Tasks:
1. Remove `proxies -> app.cache_provider` dependencies via protocol-based DI from composition root.
2. Add auth factory registration hook to minimize central registry edits for new providers.
3. Split LLM provider interfaces by capability (mountable vs endpoint-only).
4. Reduce `Any` in high-traffic business paths with typed payload aliases and narrow types.

Dependencies: Phase 2 and 3 complete.

Acceptance Criteria:
- Import direction no longer violates intended layer boundaries.
- New provider additions can be registered without editing multiple centralized branches.
- Interface segregation removes no-op method implementations.

## Compatibility + Rollback
- Compatibility:
  - Keep deprecated wrappers for one release cycle in utility and middleware modules.
  - Preserve route paths and request/response payload compatibility.
- Rollback:
  - Phase PRs are independently revertible.
  - For docs/contract changes, keep feature-flag or fallback branch during rollout.
  - If merged OpenAPI behavior diverges, retain existing custom swagger provider path as fallback.
