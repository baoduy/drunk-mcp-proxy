## Current-State Summary
- Strengths:
  - Uses FastMCP proxy composition correctly (`create_proxy` + `mount`) and stdio run path.
  - `ResourceSyncManager` already encapsulates most sync behavior and path safety checks.
- Key structural pain points:
  - `client.py` is a god-module with four concerns: data modeling, config parsing, sync service, runtime bootstrapping.
  - Runtime behavior is hard to unit test because orchestration is function-driven and intertwined with external clients.
  - DRY gaps exist in repeated resource write/path-safe logic and URI pattern parsing branches.

## Phased Plan

### Phase 1 — P0 OOP Remediation (Mandatory First)
**Goal:** Achieve strict class-first module compliance without behavior changes.

Tasks:
1. Create `StdioBridgeApplication` in `client.py` and migrate orchestration methods:
   - `bootstrap_runtime_env()` (moves line-36 side effect)
   - `create_authenticated_client()`
   - `sync_resources_on_startup()`
   - `build_server()`
   - `run()`
2. Create `ClientCliEntrypoint` in `main.py` with `run()` delegating to `StdioBridgeApplication.run()`.
3. Keep module-level adapters only for compatibility:
   - `run_stdio_bridge()` -> thin call to `StdioBridgeApplication.run()`
   - `main()` -> thin call to `ClientCliEntrypoint.run()`
4. Split model/config/sync concerns into dedicated class-first modules:
   - `resource_models.py`
   - `resource_sync_manager.py`
   - `client_config.py`

Dependencies:
- None; this is the first gate.

Acceptance Criteria:
- No module-level business orchestration outside thin adapters.
- Each module has one clear primary class.
- Existing CLI behavior unchanged.

### Phase 2 — Library-Native Built-ins (FastMCP/FastAPI)
**Goal:** Replace hand-rolled runtime wiring with framework-native abstractions where parity exists.

Tasks:
1. Validate `FastMCP.from_client(...)` parity with current flow (auth client + transforms + stdio).
2. If parity is confirmed, replace manual `create_proxy` + `mount` path with `from_client` composition.
3. Keep explicit stdio transport execution (`run(transport="stdio")`) and maintain current transform configuration.
4. Add compatibility switch/fallback to old composition in case transform/mount behavior differs.

Dependencies:
- Phase 1 complete.

Acceptance Criteria:
- Same exposed tools/resources as pre-refactor.
- No regression in startup or proxy behavior.

### Phase 3 — DRY Cleanup + Reusable Abstractions
**Goal:** Remove duplicate logic and centralize safety-sensitive operations.

Tasks:
1. Implement `_resolve_safe_path(base_dir, resource_name)` for all path checks.
2. Implement `_write_resource_content(file_path, content)` for text/blob writes.
3. Consolidate manifest/list fallback flow into a reusable sync pipeline method.
4. Extract URI matching/extraction to strategy class if multiple patterns persist.

Dependencies:
- Phase 1 complete; can run parallel with later Phase 2 validation.

Acceptance Criteria:
- Duplicate write/path logic removed.
- Security path guard enforced by one helper path.

### Phase 4 — SOLID Remediation
**Goal:** Reduce coupling and improve extension/testability.

Tasks:
1. Introduce `ResourceClientProtocol` for sync manager dependencies (DIP).
2. Isolate config loading into `ClientConfigLoader` class (SRP).
3. Separate runtime orchestration from sync internals (SRP).
4. Replace broad exception handling with narrowed exceptions and type-only logging.
5. Add/adjust tests for protocol-backed sync manager and application orchestration boundaries.

Dependencies:
- Phase 1 and Phase 3 complete.

Acceptance Criteria:
- Sync manager testable with fake protocol implementation.
- No broad silent exception paths in core resource sync flow.

## Compatibility + Rollback
- Compatibility safeguards:
  - Preserve public imports in `__init__.py` (`run_stdio_bridge`).
  - Preserve callable entrypoints (`main`, `run_stdio_bridge`) as wrappers.
  - Keep CLI arg and env precedence behavior unchanged.
- Rollback plan:
  1. If Phase 2 causes parity issues, revert to manual `create_proxy` + `mount` implementation.
  2. If module split causes import regressions, temporarily re-export moved symbols from original module.
  3. Merge each phase separately to cap blast radius.
- Blast radius:
  - Primary impact in `src/drunk_ai_client` package internals and tests touching entrypoint/runtime bootstrapping.

## Implementation Readiness
- Blockers:
  - Need explicit parity confirmation for `FastMCP.from_client` with transforms in this runtime shape.
- Open questions:
  - Are `RegexSearchTransform` and `BM25SearchTransform` mandatory for all modes?
  - Should fallback composition stay permanently behind a feature flag?
- Recommended first execution slice:
  - Phase 1, Task 1 only (`StdioBridgeApplication` introduction + compatibility wrappers) for quickest compliance progress with minimal behavioral risk.

## Quick Win + Strategic Refactor
- Quick win: extract `_resolve_safe_path` and `_write_resource_content` (small, low risk, immediate DRY/security improvement).
- Strategic refactor: split `client.py` into class-first modules around `StdioBridgeApplication` and protocol-driven collaborators.
